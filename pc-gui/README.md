# VPN Share 电脑端（图形界面版）v3.4

带图形界面的 Windows 程序，把手机上的代理 / VPN 共享给电脑使用。

> **已全面验证可用**：手机开 Gofly 全局 VPN 时，电脑经代理访问
> Google / GitHub / 百度 / 腾讯 全部正常（HTTP + HTTPS，7/7 通过）。
> 关键修复在**手机端 v1.1**（走 443 端口 DoH 绕过 fake-IP 劫持），
> 详见下文「★ 开了 VPN 反而全站 ERR_CONNECTION_CLOSED」。
>
> **请确保手机端已升级到 v1.2**（桌面 `VPN共享\VpnShare-v1.2.apk`）。

## v3.4 新增：实时流量折线图

界面上多了一块**实时流量曲线**（手机端同步也有）：

```
实时流量                    ↓ 1.85 MB/s   ↑ 128 KB/s
  ┌────────────────────────────────────────────┐
2M┤        ╭─╮                                 │
  │   ╭────╯ ╰──╮      ╭╮                      │
```

**数据从哪来**：本机中转在搬运数据时会统计双向字节（`LocalRelay.traffic()`），
GUI 每 1 秒采一次、与上次相减得到速率。所以曲线反映的是**真实经过代理的流量**，
包含浏览器、系统更新、任何走系统代理的程序。

**几个实现细节**：

| 问题 | 处理 |
|---|---|
| Y 轴量程怎么定 | 取窗口内峰值向上取整到 1/2/5×10ⁿ 的"好看"值 |
| 一次大下载后曲线被压扁 | 量程抬升立即、回落平滑（峰值 < 1/3 量程才缩） |
| 没流量时 Y 轴全是 0 | 量程下限固定 64 KB/s，保证刻度可读 |
| 采样起点误报巨峰 | 启动时以当前**累计值**为基线，第一秒不会把历史总量算进来 |
| 为什么不用 matplotlib | 会让打包体积 +30MB；Canvas 手绘零依赖、更快 |


## 直接用

双击 `release\VpnShare.exe`（或桌面 `VPN共享\VpnShare.exe`）。

## 两种使用状态（都可用）

| 手机状态 | 电脑效果 |
|---|---|
| **没开 VPN** | 正常访问**国内**网络，速度照常；国外站点 3 秒内快速报错，**不会卡死转圈** |
| **开了 VPN** | 国内外全部正常访问 |

所以**不必先开 VPN 才能用** —— 不连 VPN 时它就是一个正常的代理，国内上网畅通。

## 核心：本机中转（v3.0 新增）

系统代理不再直接指向手机，而是指向**本机的一个小中转**：

```
浏览器 ──► 127.0.0.1:8888 ──► 手机代理 ──► 手机网络出口
              （本机中转）
```

**为什么这么做？**

Windows 的系统代理是「全有或全无」——一旦指向手机，浏览器会把**所有**请求
都交给手机。手机没连 VPN 时，Google / YouTube 这类目标**连不上但不会立刻报错**，
而是一直挂到超时。浏览器只能干等，表现就是**网页一直转圈、跟断网一样**。

本机中转让它变成**快速失败**：

| 方案 | 国外站点打不开时的耗时 |
|---|---|
| 旧：直连手机 | **挂住 8 秒以上**（浏览器自己的超时，实际可能更久） |
| 新：经本机中转 | **3 秒内立即报错** |

代价是本机多一层转发（实测耗时可忽略，baidu 仍在 0.1 秒级）。

**安全性**：中转只监听 `127.0.0.1`，**不对局域网暴露**，只服务本机。

## 上不了网怎么办

**先点界面上那个橙色按钮「上网异常？点这里修复」**，然后**完全退出浏览器再重开**。

### 手机没开 VPN 时的表现（这不算故障）

**代理端口正常 ≠ VPN 在工作。** 代理只是"借道"，把流量转交给手机的网络出口：

| 手机状态 | 实际效果 |
|---|---|
| **开了 VPN** | 代理流量走 VPN 隧道 → 国内外都能访问 |
| **没开 VPN** | 代理流量走手机自己的网络 → **只能访问国内站点** |

**没开 VPN 时的实测表现**：

```
经代理访问 www.baidu.com  → 200 ✅
经代理访问 www.qq.com     → 200 ✅
经代理访问 github.com     → 200 ✅
经代理访问 www.google.com → 打不开 ❌
```

国内站点全通，Google / YouTube 打不开 —— **这是预期行为**，
因为这时手机本身就是一条普通国内网络。

**v3.0 本机中转解决了"卡死"问题**：以前这些打不开的站点会让浏览器
一直转圈（挂到超时）；现在本机中转会在 **3 秒内快速报错**，
其他网页完全不受影响。

**v2.4 起还会主动检测 VPN 状态**：启动共享前经代理去连国内直连必然打不开的站点，
不通就明确告诉你"VPN 没有生效"，而不是让你以为程序坏了。

**想访问 Google 等站点时**：回手机上把 VPN 连上（并确认是全局模式 /
分流规则覆盖了代理进程），无需重启电脑端程序，直接刷新页面即可。

### ★ 开了 VPN 反而全站 ERR_CONNECTION_CLOSED —— 根因与修复（v1.1 / v3.3）

**现象**：手机上 VPN 正常、手机本机能上外网，但电脑经代理后**所有网页**
都报 `ERR_CONNECTION_CLOSED`（或 0 字节、一直加载不出来）。

#### 根因：VPN 的 fake-IP 模式

现代 VPN 客户端（Gofly / Clash 系）常使用 **fake-IP** 模式：

```
① VPN 劫持手机 DNS —— 任何域名查询都返回 198.18.x.x 的「假地址」
   （198.18.0.0/15 是 RFC 保留段，公网根本不存在）

② 这个假地址只在 VPN 内核里有意义（内核靠自己的映射表反查回域名）

③ 代理 App 用系统解析器解析域名 → 也被劫持 → 拿到假地址
   → 拿假地址去 connect → 内核的映射表里查不到这条
   → 不知怎么路由 → 连接被重置 → 0 字节 → 浏览器报错
```

**为什么手机正常、电脑全断**：
手机本机的 App 走内核自己的解析通道，映射关系完整；
电脑的请求经代理 App 转发时，代理 App 要**自己解析**域名，拿到的却是假地址。

#### 判据：真实 IP 通、域名不通

```bash
adb shell curl -s -o /dev/null -w '%{http_code}' http://1.1.1.1/        # → 301 ✅
adb shell curl -s -o /dev/null -w '%{http_code}' http://www.baidu.com/  # → 000 ❌
```
**真实 IP 全通、域名全断** → 100% 是 DNS 层的 fake-IP 问题。

#### 修复：手机端 v1.1 走 443 端口 DoH

**53 端口的普通 DNS 查询也会被劫持**（实测：向 `223.5.5.5:53` 查询
返回的仍是 `198.18.x.x`）。所以只能用 **443 端口的加密 DoH**：

```
GET https://223.5.5.5/resolve?name=www.baidu.com&type=A
    Host: dns.alidns.com
    → {"Answer":[{"type":1,"data":"110.242.70.57"}]}   ← 真实 IP！
```

手机端 v1.1 的实现：
- 新增 `DohResolver`：DoH 服务器用 **IP 直连**（`dns.alidns.com` 主 / `doh.pub` 备），
  避免"解析 DNS 服务器域名"的鸡生蛋问题；带 TTL 缓存
- 重写 `SocketConnector`：**先用 DoH 拿真实 IP，再用真实 IP 连接**
  （旧代码用 `InetSocketAddress(host, port)`，内部会走系统解析器）
- 保留系统解析回退 —— 保证「手机没开 VPN」时国内网络共享继续可用

#### 实测结果（Gofly 全局模式）

```
电脑经 SOCKS5 → www.baidu.com    HTTP/1.1 200 OK    18523 bytes
              → www.qq.com       HTTP/1.1 302       364 bytes
              → www.google.com   HTTP/1.1 302       1884 bytes   ← google 也通
              → github.com       HTTP/1.1 301       103 bytes
https://www.baidu.com   200 OK    8807 bytes
https://www.google.com  302      1943 bytes
https://github.com      200 OK    9487 bytes
```

#### 备选方案（若不升级手机端）

1. 在 VPN App 里把 DNS 模式从 `fake-ip` 改成 `redir-host`（若有此开关）
2. 换用「热点共享」类 VPN 客户端（支持 tether 且不用 fake-ip）
3. 电脑端独立装代理客户端，不走手机转发

> ⚠️ **曾走过的弯路**：一度误判为「VPN 把局域网段 bypass 了」。
> 那个结论是**错的** —— 核查 `dumpsys` 里的 `Uids: <{0-99999}>` 可见
> 代理 App 本来就在 VPN 内。`HttpProxy` 行的 `xl=` 列表只影响
> VPN 自身的代理绕过规则，与 tun 路由无关。**真正的判据是 fake-IP。**

### 手机后台权限（防止切后台后静默失效）

Android 的省电策略会把后台 App 冻结，代理随之失效——电脑端表现为端口还在但连不通。

**v2.5 会主动做三步检查**（需手机通过 USB 连着电脑）：

1. **进程还活着吗** —— `pidof` 查代理 App 进程，被杀掉会直接告诉你"未运行"
2. **是否在电池优化白名单** —— 不在就会列出来
3. **待机桶等级** —— Active 最好，Restricted / Never 容易被冻结

发现异常会直接告诉你去哪个设置项开权限。手动设置路径：

```
手机「设置 → 应用 → 找到该 App → 省电策略」→ 设为「无限制」
并允许「自启动」和「后台运行」
```

> **重要**：如果 adb 没连上，程序会明确显示"**无法确认**"，
> 而**不是**假装"全部正常"。查不到 ≠ 没问题。

### adb 自动定位（v2.5）

后台检查 / 端口归属诊断依赖 adb。程序会按这个顺序自动找：

1. `PATH` 里的 adb
2. 环境变量 `%ADB%`
3. 常见安装位置：`%USERPROFILE%\Android\Sdk\platform-tools\`、
   `%LOCALAPPDATA%\Android\Sdk\platform-tools\`、`%ANDROID_HOME%`、
   `C:\platform-tools\` 等

**所以就算没把 platform-tools 加进 PATH，这些检查照样能用。**

### 端口归属（v2.5）

**实测结论**：手机上 `1080`（SOCKS5）和 `8080`（HTTP）**都属于 `com.vpnshare.app`**
（uid 10653）—— 也就是本工具自带的那款手机 App，它一次开了两个端口。
不是 Every Proxy 在抢端口。

实现上读 `/proc/net/tcp`（有 uid 列）做精确归属，比 `ss -tln` 可靠
（Android 的 `ss` 不带 `-p` 拿不到进程，带 `-p` 又要 root）。
**若确实拿不到归属，会直说"需 root"，不会瞎猜一个包名。**

### 关于"端口被占用"这个提示

程序**自己不占用任何端口** —— 它只改注册表 + 探测手机端口，不开任何监听。
所以提示里的"占用"两个字是**旧版文案在误导**，v2.2 已改写。

真实含义是：**那个端口能建立连接，但不响应代理协议**。常见三种原因：

1. 填的端口不是代理端口（最典型：把 PAC 端口当成了代理端口）
2. 手机端代理服务开着，但还没真正就绪（VPN 刚连上时需要几秒）
3. 手机端省电策略把代理进程冻结了

**注意：这种状态下程序不会修改你的系统代理**，浏览器照常能上网。

### 根因：手机上多个 App 抢端口（v2.3 已支持诊断）

**最容易被忽略的原因。** 手机如果装了多个 VPN / 代理类 App，
它们会抢同一个端口（`1080` / `8080` 是重灾区，几乎每个都想要）：

- 先启动的占住端口 → 后启动的报「**端口被占用**」
- 电脑端扫到这个端口**能连上**，但它不响应代理协议 → **浏览器全部卡死**

**实测案例**：手机上装了 `com.free.vpn.super.hotspot.open`（自带本地代理监听）
+ Every Proxy。前者先起来占住 1080/8080，Every Proxy 就再也起不来。
电脑连上去，两个端口对 HTTP/SOCKS5 **都是超时**。

**v2.3 的做法**：

1. 预检失败时，**自动通过 adb 查手机端哪些敏感端口在被监听**，直接写进日志
2. 提示文案明确指出"多 App 抢端口"这个最可能的原因
3. 附带处置建议：只留一个代理 App 在跑

**你的处置**：关掉多余的 VPN / 热点类 App，只保留要用的那一个。

### 伪代理识别（v2.3 已加固）

有个更隐蔽的坑：某些 App（如上面那个热点类）会开自己的 **Web 管理接口**。
收到 HTTP 请求会返回 `404` / `412` —— **有回应，但不是代理**。

旧版只判断"有回应就放行"，会把这种 Web 服务误判成代理 → 写进系统代理 → 浏览器废掉。

**v2.3 改成校验响应语义**：

| 协议 | 判定为真代理的条件 |
|---|---|
| HTTP 代理 | 状态码属于 `200` / `301` / `302` / `307` / `407` |
| SOCKS5 | 方法协商回 `05 00` 或 `05 02`，**且** CONNECT 请求有规范回应 |

明确排除 `404` / `412` / `400` —— 那是 Web 服务器，不是代理。

### 根因：只按 HTTP 探测，误杀 SOCKS5（v2.2 已修）

这是上一个版本的**判断逻辑 bug**。原来只发 HTTP 明文去探测，但手机端
SOCKS5 端口收到 HTTP 会一直等 SOCKS5 握手，**永远不回** → 被误判成"端口死了"。

实测验证（同一个 SOCKS5 端口，两种探测方式）：

```
SOCKS5 探测 -> True  (method=0x00)      ← 正确识别
HTTP   探测 -> False (ConnectionReset)  ← 误判为死端口
```

**v2.2 的修法**：

1. **HTTP 和 SOCKS5 两种协议都试**，任一有正常响应即通过
2. 探测出协议后**按协议写注册表**：SOCKS5 必须写成 `socks=host:port`
   （不写前缀 Windows 一律按 HTTP 代理处理，照样不通）
3. 自动发现改为**先识别协议再返回**，跳过"能连但不讲代理协议"的端口
4. 端口扫描顺序把 `1080` 提到最前、`8080` 挪到最后
   （8080 常是 PAC/Web 端口，优先命中就会卡住）

### 根因一：PAC 指到了代理端口（v2.1 已修）

早期版本设置系统代理时，把 `AutoConfigURL` 指向 `http://手机IP:端口/proxy.pac`，
**默认以为代理端口也提供 PAC 文件**。但实测手机端代理端口（Every Proxy 的 `1080`）
是**纯代理监听端口** —— 它只响应 CONNECT/GET 这类代理请求，**不会**用 HTTP 返回
`/proxy.pac`。

后果：浏览器去拉一个永远不响应的"文件"，把这个连接挂住，**所有网页 / 搜索全部卡死**。

实测证据（本机对着手机 `192.168.123.123`）：

```
1080 端口 TCP      -> 连得上
HTTP 代理请求      -> 无响应（超时）
SOCKS5 握手        -> 无响应（超时）
GET /proxy.pac     -> 拉不到
```

**v2.1 的修法**：

1. **默认只用手动代理**（`ProxyEnable=1` + `ProxyServer=手机IP:端口`），不再写 PAC
2. 真要 PAC 必须传入**独立的 HTTP 服务地址**，并用 `pac_url_alive()` 校验真的能返回内容
3. 启动前做**链路预检**（TCP → 协议响应 → 真实出网），**任何一步不过就拒绝改系统代理**
   —— 从根上避免"点了启动 → 浏览器直接废掉"

### 根因二：两套代理配置只改了一套

Windows 有**两套**代理配置，改一套不够：

| 位置 | 谁在用 |
|---|---|
| 注册表 `Internet Settings` 下的 `ProxyEnable` / `ProxyServer` / `AutoConfigURL` | 控制面板界面显示 |
| `Internet Settings\Connections` 下的 **`DefaultConnectionSettings`（二进制值）** | **浏览器真正读取的** |

早期版本只改了前者。结果：还原时删掉了 `AutoConfigURL` 注册表值，
但后者（二进制）里那个 PAC 地址**还留着**，浏览器照样会去拉它。

### blob 的一个隐蔽坑（v2.1 已修）

`DefaultConnectionSettings` 里字符串是 **ANSI/UTF-8 单字节**编码，**不是 UTF-16LE**：

```
[0:4]   版本号（新版 70 / 0x46）
[4:8]   修改计数器
[8]     flags：0x01直连 0x02手动代理 0x04PAC 0x08自动探测
[9:12]  保留
[12:]   4 个「长度(4字节小端=字节数) + 字符串」槽位：
        0=代理服务器 1=绕过列表 2=PAC 3=自动配置
```

按 UTF-16LE 解会得到 `瑨灴⼺ㄯ㈹...` 这种乱码，导致诊断信息完全失真
（37 字节正好等于 `http://192.168.123.123:8080/proxy.pac` 的 ASCII 长度）。

**现已全部修复**，另外：

- 程序启动时自动检查是否有残留，发现就**主动弹提示**引导修复
- 关窗 / 提权重启时按**实际状态**判断要不要清理（不再只看有没有备份记录）
- 提供上面那个一键修复按钮兜底

### 手动修复（程序也打不开时）

```bat
reg add "HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings" /v ProxyEnable /t REG_DWORD /d 0 /f
reg delete "HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings" /v ProxyServer /f
reg delete "HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings" /v AutoConfigURL /f
```

然后到「设置 → 网络和 Internet → 代理」确认「自动检测设置」和「使用代理服务器」都已关闭。

- 每次用带时间戳的**全新工作目录**，避免构建工具清理旧缓存时被删除保护拦截
- 图标 / 清单用**绝对路径**传入（构建工具以 `--specpath` 为基准解析相对路径）

## 源码结构

```

├── app.py            GUI（Tkinter）：状态卡、按钮、日志面板、三态切换
└── proxy_core.py     核心逻辑：注册表读写、端口探测、备份还原、WinINET 刷新
```

## 关键实现说明

### 相比原来的命令行脚本，修掉了什么

1. **候选 IP 不干净** —— 原版会把 `169.254.*`（APIPA，网卡没拿到 IP）加进扫描列表
2. **广播地址漏网** —— 原版过滤只排 `255.*` 开头的地址，漏掉 `192.168.x.255` 这类网段广播
3. **依赖系统网络模块的命令** —— 原版用 `Get-NetNeighbor` / `Get-NetIPAddress`，在精简系统上可能不存在
4. **中文编码** —— 终端下 `arp -a` 输出是 GBK，按 UTF-8 解码会抛异常并丢掉整个结果
5. **黑窗口不可读** —— 成功失败都靠一行行文字，看不清

新版全部规避：用 `arp -a` 拿邻居表并按 GBK 稳健解码、显式过滤无效地址、GUI 自带日志面板。

### 为什么不强制 UAC 提权

设置系统代理写的是 `HKCU` 注册表，**普通用户权限就能改**，刷新 WinINET 也是进程内 API 调用。
强制提权只会让每次启动都弹窗。所以清单用 `asInvoker`，界面提供「以管理员重启」按需使用。

### 还原的正确性

还原时逐字段恢复 `ProxyEnable` / `ProxyServer` / `AutoConfigURL` / `ProxyOverride`，
并删除备份键。实测还原后与原始值**逐字段一致**。没有备份记录时退化为「清空代理恢复直连」。

### 一个容易误判的点

**端口能连通 ≠ 代理真的可用。** 端口通只代表有个进程在听，不代表它会讲代理协议。
实测就遇到过：端口 TCP 连得上，但 HTTP / SOCKS5 请求**全部无响应**
（这种"端口活着、代理死了"的状态，一旦设成系统代理，浏览器所有请求都会卡死）。

所以 v2.1 的预检分三级，并明确报出卡在哪一级：

| 级别 | 检查 | 失败提示 |
|---|---|---|
| 1 | TCP 能否连通 | 手机代理没开 / 不在同一热点 / 没监听 0.0.0.0 |
| 2 | 发代理请求有无响应 | 端口是"哑端口"，代理服务没真正启动 |
| 3 | 通过代理能否出网 | VPN 没连 / 不是全局模式 |

**任一级失败都不写系统代理**，只弹窗说明原因 —— 保证浏览器始终可用。
